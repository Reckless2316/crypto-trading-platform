L96: ##
L97: 
L98: cite14†​ L99: 
L100: Request rules
L101: 
L102: These rules apply to every request:
L103: 
L104: Rule  | Limit
L105: --- | ---
L106: Body size  | At most 32 MiB. Headers don’t count.
L107: Encoding  | UTF-8 JSON without a byte order mark (BOM).
L108: Nesting  | At most 64 nested levels of objects and arrays in each of `state`, `instructions`, and `criteria`. Flatten deeper content.
L109: Numbers  | Finite numbers only. `NaN`, `Infinity`, and numbers too large to represent, such as `1e400`, are rejected. Send identifiers and exact large quantities as strings.
L110: A body over 32 MiB returns `413`; the other rules return `400`.
L111: ###
L112: 
L113: cite15†​ L114: 
L115: Compression
L116: 
L117: You can compress the body with `Content-Encoding: gzip` (or `x-gzip`) or `zstd`. The SDKs compress request bodies of 1 KiB or more with zstd when the runtime supports it. Use one compression layer, and keep zstd’s window at most 8 MiB. The 32 MiB limit applies to both the compressed and the decompressed body. An unsupported `Content-Encoding` or more than one layer returns `415`; a malformed compressed body returns `400`.
L118: ##
L119: 
L120: cite11†​ L121: 
L122: Question types
L123: A `Question`’s type is set by its `type` field. Every question has `type` and `instructions`, and most types also take `criteria`; each type’s page says what it accepts. The `instructions` property can be a string, an object, or an array. You can break up a long question that has extra context, or data it needs to reference, into a structured object.
L124: Put the question in one field and the data in the others, and refer to the data fields by name in backticks, the same way you point a question at a nested `state` value:
L125: 
L126:     `"instructions": {
L127:       "potential_duplicate": {
L128:         "name": "John Smith",
L129:         "location": "Oakland, California",
L130:         "last_employer": "Google"
L131:       },
L132:       "question": "Is the resume for the same person as `potential_duplicate`?"
L133:     }
L134:     `
L135: See cite16†Use structure in the questions to learn more.

L580: cite57†​ L581: 
L582: Errors
L583: 
L584: Errors use standard HTTP status codes with a JSON body describing what went wrong.
L585: Status  | Meaning
L586: --- | ---
L587: `400 Bad Request`  | The body breaks a cite14†request rule , such as invalid UTF-8, too much nesting, a number that isn’t finite, or a malformed compressed body. With `max_tokens_exceeded`, the request is longer than the model’s cite9†context length .
L588: `401 Unauthorized`  | Missing or invalid API key. Check the `Authorization` header.
L589: `413 Payload Too Large`  | The body is over 32 MiB. See cite14†Request rules .
L590: `415 Unsupported Media Type`  | The body uses an unsupported `Content-Encoding` or more than one compression layer. See cite15†Compression .
L591: `422 Unprocessable Entity`  | The request body failed validation, for example a missing required field or a malformed question. The body details the offending field.
L592: `429 Too Many Requests`  | You have exceeded your rate limit. Back off and retry after a short delay.
L593: `529 Overloaded`  | TypeSafe is temporarily overloaded. Retry after a short delay.
L594: ###
L595: 
L596: cite58†​ L597: 
L598: Handling rate limits
L599: 
L600: When you receive a `429 Too Many Requests` or `529 Overloaded` response, retry the request with exponential backoff instead of retrying immediately. Our client SDKs handle this automatically, so no extra handling is needed if you use one of our SDKs with its default retry policy.

L19: # Models
L20: 
L21: Copy page Copy page
L22: 
L23: Jev is TypeSafe’s flagship model and the first cite3†System One model . Every model on this page is served by the same endpoint, `POST /v1/systemone`. The request’s `model` field selects which one handles the call; see the cite4†API reference for the full request shape.
L24: ##
L25: 
L26: cite5†​ L27: 
L28: Current models
L29: 
L30:  | Jev 1.14  | Jev 1.13
L31: --- | --- | ---
L32: Model ID  | `jev-1.14.0`  | `jev-1.13.0`
L33: Price (per Btok / per Mtok)  | $42 / $0.042  | $42 / $0.042
L34: Context length  | 64k per-request / 32k per-question  | 64k per-request / 32k per-question
L35: Input  | Text  | Text
L36: 
L37: Jev 1.14 is the newest Jev release, available from October 14, 2026.
L38:   * Price: You pay per input token. Output tokens are free. A Btok is a billion tokens and an Mtok is a million tokens.
L39:   * Context length: Two limits, the per-request context and the per-question context. See cite6†Context length . To raise both, see cite7†Long context .
L40:   * Input: Jev reads natural-language text, sent as a string, a JSON object, or an array of text values. It does not accept audio or video. Convert those into text or structured fields before you send them as `state`. See cite8†State for the shapes `state` accepts.
L41: ##
L42: 
L43: cite6†​ L44: 
L45: Context length
L46: 
L47: Jev ingests the `state` once and evaluates every question against it in parallel. A request has to fit two context limits:
L48:   * Per-request context (`per_request_context`): the `state` plus all questions combined.
L49:   * Per-question context (`per_question_context`): the `state` plus any one question.
L50: There is no separate limit on the number of questions in a request. Any number of questions is allowed as long as the request fits both limits. See cite9†Speculative fan-out for packing many questions into one request, and cite10†Jev 1.13 jaggedness for how accuracy shifts as the state grows. To raise both limits, see cite7†Long context .
L51: ###
L52: 
L53: cite7†​ L54: 
L55: Long context
L56: Long context is off by default and works on both Jev 1.14 and Jev 1.13. To turn it on, send the `TypeSafe-Danger-Zone-Long-Context: true` header with each request that needs it. With the header, the per-request context and the per-question context are both 262k tokens. Requests without the header keep the default limits in the table above.
L57: 
L58:     `curl https://api.typesafe.ai/v1/systemone \
L59:       -H "Authorization: Bearer $TYPESAFE_API_KEY" \
L60:       -H "Content-Type: application/json" \
L61:       -H "TypeSafe-Danger-Zone-Long-Context: true" \
L62:       -d '{
L63:         "model": "jev-latest",
L64:         "state": "<a long contract, transcript, or record>",
L65:         "questions": {
L66:           "has_termination_clause": {
L67:             "type": "noul",
L68:             "instructions": "Does the `state` include a clause that lets either party end the agreement early?"
L69:           }
L70:         }
L71:       }'
L72:     `
L73: Long context costs the same per token as any other request. It is slower and less accurate than staying within the default limits, so turn it on only for requests that need it.
L74: ##
L75: 
L76: cite11†​ L77: 
L78: Rate limits
L79: Rate limits are set per organization. Your organization’s current limits are in the cite12†developer console†console.typesafe.ai . Limits are measured in tokens per second and requests per second. A request over either limit returns `429 Too Many Requests`. Our cite13†client SDKs retry these requests by default, waiting longer between each attempt, and follow the `retry-after` header when the response includes one. If you call the HTTP API directly, see cite14†Handling rate limits .
L80: Higher limits are available on custom and enterprise plans. Contact sales@typesafe.ai.
L81: ##
L82: 
L83: cite15†​ L84: 
L85: Aliases
L86: 
L87: An alias is a model name that points to a versioned model ID. Send it in the `model` field the same way you send a model ID.
L88: 
L89: Alias  | Points to  | Meaning
L90: --- | --- | ---
L91: `jev-latest`  | `jev-1.13.0`  | The most recent stable, official release. The default in our client SDKs, and the name the examples in these docs use.
L92: `jev-preview`  | `jev-1.14.0`  | The most recent release, official or not. Moves ahead of `jev-latest` when a preview build is available.
L93: An alias moves when a new release ships, so its answers can change without any change to your code. Each response’s `model` field gives the versioned ID that answered, so you can log which model produced each result. If you have tuned confidence thresholds against one version, send that version’s ID instead of the alias, and switch to the new version when you are ready.
L94: ##
L95: 
L96: cite16†​ L97: 
L98: Customizing Jev
L99: 
L100: Jev is not fine-tuned or LoRA-adapted with customer data. It is trained with cite17†RLCD to return calibrated decisions, and the same weights serve every account. You shape its answers to your domain through the request rather than through per-account weights:
L101:   * Put your proprietary content, records, and reference material in the `state` field. See cite8†State .
L102:   * Encode your domain rules and boundary cases in the `instructions` and `criteria` of each question. See cite18†How to build with TypeSafe and cite19†Advanced: structure .
L103:   * Decompose broad judgments into atomic questions and combine the outputs in code. See cite20†Composite scoring and the cite21†AutoResearch cookbook for training a downstream classical model on Jev’s probabilities.
L104: ##
L105: 
L106: cite22†​ L107: 
L108: Language support
L109: 
L110: Jev accepts natural-language text. English is the primary training language and where accuracy is currently best. Other languages, including CJK scripts, are handled but not equally well; test on your own content before relying on Jev for a non-English workload, and pay close attention to cite23†Confidence when routing.
L111: ##
L112:

L115: Data handling
L116: 
L117: Jev is not trained on customer requests or responses. See cite25†Legal for the Data Processing Agreement, the Privacy Policy, and details on zero data retention (ZDR) for enterprise customers.
