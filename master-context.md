## Role and accounting boundaries

The target is four operating roles: authority alone owns venue credentials, ledger writes, reservations, reconciliation and order dispatch; REFLEX sees numeric state and returns typed judgments; BRAIN consumes session/research evidence and proposes bounded changes; dashboard reads projections and forwards authenticated operator commands. Code owns thresholds, size, order semantics, eligibility, and every side effect. Models cannot arm, clear incidents, activate releases, or approve their own output.

Existing useful kernels include `bot/autonomous/execution.py:151` (`OrderAuthority`), `:48` (`PaperVenue`), `bot/autonomous/worker.py:64` (`PaperWorker`), `bot/autonomous/nightly.py:200` (`review_session`) and `:290` (`review_account_activity`). These are partial building blocks. `VenuePort` currently exposes only `submit` (`execution.py:40`), the worker's `--role` prints a provider-secret allowlist (`worker.py:642`), and BRAIN has deterministic/unavailable implementations (`brain.py:33`, `:51`). None establishes the complete role deployment or verified external BRAIN provider.

The current dashboard still has legacy SQLite account state (`app.py:236`) and accesses a paper ledger at `/tmp/paper-serve-ledger.sqlite3` (`:1309`, `:1343`, `:1369`). Its kill handler opens that ledger for writing (`:1561`), violating the eventual single-writer process boundary. Its arm handler changes local runtime state without an authenticated operator session (`:1302`). These observed behaviors require integration work; rejecting direct fills alone does not complete Task 17.
